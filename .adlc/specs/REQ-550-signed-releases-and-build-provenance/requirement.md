## Description

Three supply-chain gaps around the release pipeline are known and recorded but
unfixed. This REQ closes them as one effort, because they share the same
workflow files, the same secrets, and the same verification story.

1. **Unstable executable identity.** macOS Keychain ACL grants bind to the
   identity of the requesting executable. Released binaries are ad-hoc signed
   (whatever the arm64 linker emits), so identity changes with every build:
   every `brew upgrade` costs each user a fresh Keychain consent prompt for
   `teton-code` — the daemon that resolves `keychain://` credentials at call
   time. A stable Developer ID signing identity makes grants survive upgrades,
   turning the one-time re-prompt REQ-549 accepted into the *last* re-prompt
   (REQ-549 OQ-2, LESSON-457).

2. **No build provenance.** `checksums.txt` is published beside the artifacts
   it describes, over the same channel, mutable by the same principals — a
   direct-download verifier only learns that the release page agrees with
   itself. (Homebrew users are partially covered today: the tap's pinned
   `sha256` lives in a different repo behind a different token.) Deferred from
   REQ-548's verify pass: attest artifacts with
   `actions/attest-build-provenance` and verify with `gh attestation verify`.

3. **Repository-scoped secrets.** `HOMEBREW_TAP_TOKEN` and the `GCP_*`
   secrets are repository secrets, readable by any workflow on any ref. The
   tap token is the highest-value credential in the design — it rewrites the
   formula every `brew install` executes. Deferred from REQ-548's verify
   pass: move them to GitHub Environments with deployment rules restricted to
   release tags and `main`, plus `assertion.ref` conditions on the WIF side.

All three were deliberately deferred in REQ-548 because they need repo-admin
or Apple-account actions the pipeline cannot perform; this REQ scopes the
human steps explicitly instead of leaving them implicit.

## System Model

### Entities

| Entity | Field | Type | Constraints |
|--------|-------|------|-------------|
| SigningIdentity | kind | enum(developer-id-application) | required; one stable identity across releases (BR-1) |
| SigningIdentity | team_id | string | required; constant across releases — identity stability is the point |
| SigningIdentity | storage | enum(ci-secret-p12, runner-keychain) | resolved at architecture time (OQ-2) |
| SignedArtifact | signature | codesign blob | required for every macOS binary in every tarball (BR-1) |
| SignedArtifact | verified_by | enum(codesign, spctl) | release smoke verifies per artifact (BR-6) |
| Attestation | subject_digest | sha256 | MUST be computed from the uploaded bytes in the same run (mirrors REQ-548 BR-5) |
| Attestation | predicate | slsa-provenance | generated by `actions/attest-build-provenance` |
| GitHubEnvironment | name | enum(tap-publish, site-deploy) | deployment branch/tag rules: `v*.*.*` and `main` only (BR-4) |
| GitHubEnvironment | secrets | list | `HOMEBREW_TAP_TOKEN` → tap-publish; `GCP_*` → site-deploy; none remain repository-scoped (BR-4) |

### Events

| Event | Trigger | Payload |
|-------|---------|---------|
| artifacts_signed | release build completes per target | artifact, identity, signature |
| attestation_published | after artifact upload, same workflow run | subject digest, provenance predicate |
| attestation_verified | release smoke + runbook step | artifact, verify exit classification |
| secret_access_denied | workflow on a non-release ref requests an environment secret | ref, environment (this failing closed is the feature) |

### Permissions

| Action | Roles Allowed |
|--------|---------------|
| Hold/renew the Developer ID certificate | Apple Developer account owner (user) |
| Configure GitHub Environments + deployment rules | repo admin (user — UI-only, pipeline cannot) |
| Sign + attest artifacts | release workflow on `v*.*.*` tags only |

## Business Rules

- [ ] BR-1: Every macOS binary in every released tarball is signed with the
      same Developer ID identity (stable team id) across releases. The
      user-visible contract: a Keychain grant given to release N survives
      upgrade to release N+1 with no re-prompt (informed by LESSON-457,
      REQ-549 OQ-2).
- [ ] BR-2: A missing or failed signature fails the release loudly — the
      pipeline must never fall back to shipping ad-hoc-signed binaries
      because the certificate was absent or expired. The guard must not be
      keyed on the certificate's presence (a cert-absent run skipping the
      signing step and passing is the self-disabling-guard shape — informed
      by LESSON-443, LESSON-447).
- [ ] BR-3: Provenance attestations are generated in the same workflow run
      that built the artifacts, from the actually-uploaded bytes — never
      re-computed or hand-supplied (mirrors REQ-548 BR-5); `gh attestation
      verify` of every artifact is a release gate and a documented runbook
      step.
- [ ] BR-4: No release credential remains repository-scoped. Stated as a
      property, not a location: EVERY credential-bearing step across ALL
      workflows (`release.yml`, `deploy-site.yml`, and any future one) draws
      its secret from a GitHub Environment whose deployment rules restrict it
      to `v*.*.*` tags and/or `main`, with matching `assertion.ref` WIF
      conditions for cloud credentials (informed by LESSON-455 — the partial
      fix that pins one file is the failure mode here).
- [ ] BR-5: Every new verification gate is proven by a known-bad fixture in
      `tools/release/selftest.sh`: a tampered artifact must fail attestation
      verification, an unsigned/ad-hoc binary must fail the signature gate,
      and the selftest asserts both go red (informed by LESSON-454 — a gate
      is only a gate if a known-bad input makes it fail).
- [ ] BR-6: Signature and attestation checks run per artifact per platform in
      the release smoke — a green arm64 leg is not evidence for the x86_64
      tarball (informed by LESSON-433). Linux artifacts are explicitly
      unsigned in v1 and the release notes say so (honesty posture of
      REQ-548 BR-10).
- [ ] BR-7: New gate scripts classify their exits: "verification FAILED"
      (tampered/unsigned — blocks release) is a distinct exit code from
      "could not verify" (network/tooling — EXIT 75 UNCHECKED convention),
      and neither collides with an uncaught-failure default (informed by
      LESSON-442).

## Acceptance Criteria

- [ ] AC-1: On a released tarball: `codesign --verify --strict` and
      `codesign -dv` show the Developer ID identity and constant team id for
      `teton` and `teton-code`; the release smoke asserts this per macOS
      target.
- [ ] AC-2: `gh attestation verify <artifact> --repo atelier-fashion/teton-code`
      succeeds for every published artifact of a release, in CI and as a
      copy-pasteable runbook command in the README/release notes.
- [ ] AC-3: The selftest proves both gates can fail: a byte-flipped tarball
      fails attestation verification and an ad-hoc-signed stand-in fails the
      signature gate, each with the correct exit classification (BR-5, BR-7).
- [ ] AC-4: `HOMEBREW_TAP_TOKEN` and `GCP_*` no longer appear as repository
      secrets; a manually-dispatched workflow on a non-release ref cannot
      read them (verified by a deliberate failing probe run, recorded in the
      REQ). Environment protection rules are screenshotted/recorded since
      GitHub settings are not in-repo state.
- [ ] AC-5: The tag-driven release workflow is green end-to-end with signing
      and attestation on all three targets, with no manual step beyond tag
      push (preserves REQ-548 AC-3).
- [ ] AC-6: Keychain-grant survival across an upgrade (BR-1's user-visible
      contract) is human-verified once two consecutively signed releases
      exist — staged like REQ-548 AC-4: the criterion is defined now, first
      exercisable at the second signed release, and recorded as unrun until
      then (informed by LESSON-433's unrun-legs-recorded-as-unrun posture).

## External Dependencies

- Apple Developer Program membership (paid, user decision) and a Developer ID
  Application certificate — blocks BR-1/AC-1; everything else can ship
  without it (OQ-1 sequencing).
- GitHub repo admin access for Environments configuration (UI-only — the
  exact reason REQ-548 deferred these findings).
- `actions/attest-build-provenance` + workflow permissions `id-token: write`,
  `attestations: write`; `gh` ≥ attestation-verify support on runners.
- Possibly `notarytool` / App Store Connect API key if notarization enters
  scope (OQ-3).

## Assumptions

- Distribution remains brew-only (no direct-download links on the landing
  page), so Gatekeeper quarantine — and therefore notarization — is not yet
  load-bearing; signing alone stabilizes Keychain identity, which is the
  driving user pain (REQ-549). If REQ-548 OQ-4 ever adds direct downloads,
  notarization becomes mandatory and this assumption breaks.
- The signing step can run on GitHub-hosted macOS runners (cert imported into
  a temporary keychain from a CI secret) — the common pattern; if org policy
  forbids exporting the cert, OQ-2's runner-keychain alternative applies.
- REQ id allocated with remote verification (no degradation warning from the
  allocator).

## Open Questions

- [ ] OQ-1: Sequencing — provenance + environment-gating need no Apple
      account and could ship immediately; signing waits on the Developer ID
      cert. One REQ in two phases, or split? (Recommend: one REQ, two
      dependency tiers, so the property-scoped secret work (BR-4) is never
      split across efforts — LESSON-455.)
- [ ] OQ-2: Certificate storage: base64 P12 in an environment-gated secret
      imported into a throwaway keychain per run (common, revocable), or a
      dedicated self-hosted runner holding the cert (heavier, never exports
      the key)?
- [ ] OQ-3: Is notarization in scope now (future-proofs direct downloads,
      adds notarytool credentials + stapling to the pipeline) or deferred
      until REQ-548 OQ-4 resolves? Related: does the brew install path strip
      the quarantine attribute for these artifacts in practice?
- [ ] OQ-4: Should the formula's `test do` block also run
      `codesign --verify`, giving every user machine a local signature check
      at install time?

## Out of Scope

- Windows signing (platform unsupported) and Linux binary signing/GPG — v1
  Linux artifacts ship unsigned, stated honestly (BR-6).
- Sigstore/cosign beyond GitHub's native attestation; SBOM generation.
- Direct-download distribution itself (REQ-548 OQ-4 — this REQ only removes
  the signing blocker for it).
- Rotating the tap-token *kind* (fine-grained PAT vs deploy key) — only its
  scoping changes here.
