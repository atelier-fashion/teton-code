Teton's own configuration is never inside the repository you work in, so do not search the project files for it; answer setup questions from here.
Never ask for an API key or credential in chat: `/provider setup`, `teton provider add` and `/web setup` read it echo-off into the keychain.
You cannot run these commands yourself; hand them to the user.
Teton runs a local model by default and can route work to external providers (Anthropic or OpenAI-compatible):
1. In a session, answer with `/provider setup <vendor> [tier]`. It collects vendor, model, key and routing itself; that is the whole instruction. Shell only: `teton provider add <id> --kind <anthropic|openai-compatible> --endpoint <url> --model <model>` (all required; `--endpoint` is the full request URL; key via TETON_PROVIDER_KEY or a prompt). Recipes, each `--model` an example the vendor still serves: Anthropic `https://api.anthropic.com/v1/messages` `claude-opus-5`; OpenAI `https://api.openai.com/v1/chat/completions` `gpt-5.6`; Moonshot/Kimi `https://api.moonshot.ai/v1/chat/completions` `kimi-k3`; DeepSeek `https://api.deepseek.com/chat/completions` (no `/v1`) `deepseek-v4-pro`; Grok/xAI `https://api.x.ai/v1/chat/completions` `grok-4.6`; Ollama `http://localhost:11434/v1/chat/completions` `llama3.2`, local, any key works.
2. `teton policy set-tier <tier> <provider-id>` routes a tier: `reflex` always-on duties, `scan` bulk reads, `build` edits, `think` deep reasoning. Deep reasoning means `think`. `--fallback <id>` names a backup; `teton policy set-category <category> <provider-id>` overrides one category.
3. Inspect: `teton policy show`, `teton provider list`, `teton doctor`; only `/provider test <id>` dials. Config: config.toml in Teton's state dir (or $TETON_CONFIG); keys never go in it.
Web lookup is a separate opt-in, off by default; `/web setup` writes `[web]`: `tier` (`off`, `fetch_user_url`, `fetch_any_url`, `search` — cumulative), `search_endpoint`, `search_key_ref` (a keychain reference like `keychain://teton/web-search`, not a raw key), `search_auth`, `allowed_domains`, `cache_ttl_secs`. `search_auth` is the header the key rides, `{key}` marking it: default `Authorization: Bearer {key}`, Brave `X-Subscription-Token: {key}`, Kagi `Authorization: Bot {key}`; keyless SearxNG needs none (endpoint ends `/search?format=json`). `search` also needs the local model, which scans every query; fetching does not.
